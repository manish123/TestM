# Panchang Knowledge Base

This repository defines the content model and editorial specification for the Panchang.cloud Knowledge Base.

The Knowledge Base is intended to make Panchang understandable and practically usable: not merely to report a time, but to explain what the concept means, why it exists, how it is determined, how it has traditionally been interpreted, and how a person can use it responsibly.

## Current scope

This repository contains content, schema, graph metadata and templates. The Panchang.cloud rendering/knowledge engine is the next implementation phase.

The production target is a **static knowledge layer under the same Panchang.cloud domain**:

`https://panchang.cloud/knowledge/{slug}`

The knowledge layer must not alter the existing dynamic Panchang application routes or duplicate Panchang calculation logic.

## Canonical content structure

Every knowledge concept follows the same core sequence:

1. What is it?
2. Why does it exist?
3. How is it calculated?
4. Traditional interpretation
5. How to use it
6. Common misconceptions
7. Today's calculation
8. Sources
9. Related concepts

## Editorial principles

- Distinguish traditional claims from astronomical/calendrical computation and practical guidance.
- Do not present traditional interpretations as scientific causation.
- Prefer identifiable primary/classical sources and clearly identify the source tradition where relevant.
- Explain the calculation rather than treating the Panchang output as a black box.
- Connect concepts to current, location-aware Panchang calculations where applicable.
- Avoid content written solely to target search keywords.
- One canonical knowledge entity should absorb aliases and synonymous search terms rather than creating duplicate articles.
- Related concepts use canonical entity IDs from `schema/knowledge-index.yaml`; display names are resolved by the engine.
- Current dates and times belong to the calculation engine, not hard-coded article content.
- Publication is controlled by one status vocabulary: `draft`, `established`, `reviewed`, `published`, `deprecated`. Only `established`, `reviewed` and `published` are eligible for production publication.

## SEO policy

SEO metadata is part of the content contract, but SEO HTML is generated by the static builder.

Each article may provide:

- `seo.title` — optional page-title override.
- `seo.description` — unique, human-readable search/social description.
- `seo.og_image` — optional social preview image.
- `seo.noindex` — explicit exception when a page should not be indexed.

The engine generates from this metadata and the canonical slug:

- `<title>`
- `<meta name="description">`
- self-referencing `rel="canonical"`
- Open Graph/social metadata
- robots directives where explicitly required
- `Article` and `BreadcrumbList` structured data where applicable
- sitemap entries for publishable entities
- language alternates when localized pages actually exist

Do **not** add `meta keywords`. Google Search does not use the keywords meta tag for ranking. The article's actual content, headings, internal links and descriptive metadata are the SEO inputs that matter.

## Current knowledge corpus

The content directory currently contains **28 canonical knowledge entities**. `schema/knowledge-index.yaml` is the canonical entity and relationship registry and must remain synchronized with the content corpus.

## Next phase: Knowledge Engine

The engine should be deliberately small and deterministic:

`TestM Markdown/YAML → validation → graph resolution → static HTML → /knowledge/*`

It should:

1. Parse and validate frontmatter.
2. Reject duplicate IDs/slugs.
3. Enforce the publication allowlist.
4. Resolve every `related_concepts` ID against the knowledge index.
5. Generate canonical URLs and redirects for aliases.
6. Render Markdown as crawlable HTML at build time.
7. Generate SEO metadata and structured data from the content contract.
8. Generate a sitemap containing only publishable pages.
9. Leave current Panchang APIs untouched.
10. Treat the `Today's calculation` section as a controlled integration point for existing Panchang APIs; V1 may render a CTA instead of embedding live calculation data.

The engine must never reimplement Swiss Ephemeris/Panchang calculations inside the knowledge repository.
